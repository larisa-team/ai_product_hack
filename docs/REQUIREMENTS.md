# Требования: Интеллектуальный аналитический центр

> Консолидированные вводные: кейс организаторов + [`../PROJECT_SCENARIOS_AND_FILTERS.md`](../PROJECT_SCENARIOS_AND_FILTERS.md) + решения команды.

## 1. Кейс

### Боль

Служба по связям с общественностью и государственными органами (PR/GR) ежедневно тратит
**3–4 часа** на ручной мониторинг информационного поля: десятки СМИ, сайты регуляторов,
Telegram-каналы, отраслевые дайджесты. Цель мониторинга — вовремя увидеть:

- упоминания компании и конкурентов;
- изменения в нормативно-правовой базе (НПА);
- отраслевые тренды и кризисные сигналы.

Информация разрознена, саммари пишутся вручную, решения принимаются с задержкой.

### Пользователи

| Роль | Как пользуется |
|---|---|
| PR-менеджер | мониторинг репутации, упоминаний, кризисных сигналов |
| GR-специалист | отслеживание НПА и инициатив регуляторов |
| Руководитель подразделения | стратегические дайджесты за период |

### Что требуется

Работающий **прототип** аналитического центра (веб-приложение), который автоматически собирает,
структурирует и саммаризирует отраслевые новости в едином интерфейсе, с гибким ручным управлением
источниками и контентом.

### MVP-чеклист организаторов

- [ ] Сбор данных минимум из **5 источников разных типов**.
- [ ] Автоматическая саммаризация минимум **10 последних материалов** (демонстрируется на защите).
- [ ] Дашборд с **фильтрацией и поиском**.
- [ ] **Добавление, редактирование, удаление источников**.
- [ ] **Редактирование метаданных и саммари** публикаций.
- [ ] Три категории источников: СМИ/агрегаторы (RSS, API); сайты регуляторов (ЦБ РФ, Госдума,
      Правительство РФ, Роспотребнадзор и др.); Telegram-каналы и дайджесты.
- [ ] Интеллектуальная обработка: саммари в 3–5 предложений + сущности (кто/что/когда/последствия);
      категоризация (регуляторика / репутация / конкуренты / тренды); приоритизация
      (высокая / средняя / низкая).
- [ ] Управление данными: добавление источника по URL; редактирование заголовка, саммари, категории,
      приоритета, тегов; удаление/скрытие источника или публикации; ручное добавление материала.

### Целевая метрика

**Время обработки + ценность без лишнего шума.** Демо должно наглядно показывать: сколько
материалов обработано за какое время, сколько признано релевантным, сколько убрано из поля зрения
как шум.

### Тестовые данные

Оффлайн-архив из **50+ новостных статей и НПА** — для отладки саммаризации и категоризации без
зависимости от внешних API. Используется как источник типа `archive` и как основа демо.

### Вне скоупа хакатона

- промышленная нагрузка и отказоустойчивость;
- информационная безопасность;
- отдельные модальности (аудио/видео/изображения);
- мультипользовательский режим, аутентификация, разграничение доступа.

## 2. Ключевые сущности

| Сущность | Что это |
|---|---|
| **Проект мониторинга** | Центральная сущность. Профиль: тема/отрасль, отслеживаемые компании и персоны, интересующие категории, период первичного сбора, подключённые источники, стоп-темы (`negative_prompt`), правила ранжирования, частота обновления, история обработанного. |
| **Событие (NewsItem)** | Единица ленты. Один факт, о котором сообщили один или несколько источников; агрегирует ссылки на все первоисточники. Содержит саммари, сущности, тип, категорию, важность. |
| **Источник (Source)** | RSS-лента, сайт регулятора, Telegram-канал, оффлайн-архив или ручной ввод. Хранит время последнего сбора. |
| **Правило (RankRule)** | Управляемая пользователем единица ранжирования: условие → действие (поднять / понизить / закрепить / скрыть) с весом. Два вида: `field` (по полям карточки) и `semantic` (по смыслу). |

Два входных сценария (из [`../PROJECT_SCENARIOS_AND_FILTERS.md`](../PROJECT_SCENARIOS_AND_FILTERS.md)):

1. **Проекта ещё нет** — визард создания: профиль → источники → предпочтения → сбор за период →
   ранжированная лента → корректировка → сохранение проекта и расписания.
2. **Проект сохранён** — фоновое обновление по расписанию → новые события с применёнными
   сохранёнными правилами → проверка и обратная связь пользователя → при необходимости
   сохранение новых настроек → дайджест за период.

## 3. Журнал решений команды

Каждое решение — что делаем и почему.

### Р1. Формат, стек, ограничения

**Решение:** веб-приложение; backend **Python + FastAPI**, frontend **React + Vite**; хранилище
**SQLite**; срок ~24–36 ч; команда 3–5 человек. LLM-провайдер заранее не выбран.
**Почему:** веб даёт лучшую наглядность на защите и проще всего закрывает требования по
фильтрам/поиску/редактированию. Python — самая зрелая экосистема для парсинга (RSS, HTML,
Telegram) и работы с LLM. SQLite — zero-config и даёт полнотекстовый поиск (FTS5) из коробки.
Провайдер абстрагируем, чтобы демо не падало из-за внешних лимитов.

### Р2. Инкрементальный сбор

**Решение:** у каждого источника хранится `last_fetched_at`; при сборе берём только материалы
новее этой метки. Первый сбор ограничен выбранным периодом проекта, дальше — только дельта.
**Почему:** не переобрабатываем одно и то же (экономия времени и вызовов LLM — прямое влияние
на целевую метрику), лента не «прыгает».

### Р3. Единица ленты — событие, кросс-источниковая дедупликация обязательна

**Решение:** в ленте показываем **событие (NewsItem)**, а не отдельную публикацию. Похожие
сообщения из нескольких Telegram-каналов и с сайта схлопываются в одну карточку с несколькими
ссылками на источники. Это фича MVP, не стретч.
**Почему:** специалист сейчас тратит время именно на то, чтобы понять, что «десять постов про
одно и то же». Одна карточка на факт = меньше шума, быстрее принятие решения. Плюс несколько
подтверждающих источников — полезный сигнал достоверности.

### Р4. Саммаризация в контексте профиля проекта

**Решение:** в запрос к LLM на саммаризацию и выделение сущностей передаётся профиль проекта —
отрасль/тема и список отслеживаемых компаний. Саммари и сущности формируются с учётом этого
контекста (что важно именно для этого пользователя, последствия для его бизнеса).
**Почему:** обобщённое саммари может упустить деталь, критичную для конкретной отрасли или
компании. «Медленная» часть профиля (отрасль, компании) меняется редко — её безопасно «зашивать»
в саммаризацию.

### Р5. Минимальный structured output LLM

**Решение:** LLM возвращает строго и только:
`{ title, summary (3–5 предложений), entities {who, what, when, consequences}, doc_type (npa|news),
category (регуляторика|репутация|конкуренты|тренды), importance (high|medium|low) }`.
Дополнительных флагов (слухи, «тема ИИ», конкурент как главный объект и т.п.) не заводим.
**Почему:** это ровно то, что требует кейс, и не больше. Всё остальное, что нужно фильтрам,
проверяется правилами по ключевым словам в тексте — дешевле, прозрачнее, не раздувает контракт.

### Р6. Ранжирование — только правила пользователя (+/−)

**Решение:** позиция события в ленте = **сумма весов сработавших правил проекта** (вес со знаком).
Никакого скрытого композитного «умного балла», без ML.
**Почему:** специалист всё равно ранжирует по своей методике. Ему нужен прозрачный, полностью
управляемый инструмент, а не чёрный ящик. Каждая позиция объясняется списком сработавших правил.

### Р7. Два вида правил: `field` и `semantic`

**Решение:**
- `field` — условие по полям карточки (`importance`, `doc_type`, `category`, `entities.who`,
  regex по `title`/`summary`/`body`, `source_id`, `age_days`, `source_count`) → ± вес.
- `semantic` — косинусная близость эмбеддинга карточки к эталонному тексту (по умолчанию — строка
  профиля) → действие пропорционально близости, либо скрытие ниже порога.
**Почему:** `field` покрывает точные, понятные условия. `semantic` нужен, когда «по смыслу не то»
трудно выразить списком слов, и чтобы быстро сфокусировать ленту, не листая всё подряд.

### Р8. Три разные вещи, которые называют «фильтром»

**Решение:** разводим терминологию:
| Механизм | Когда | Эффект | Обратимость |
|---|---|---|---|
| Жёсткий отбор | до LLM | материал не попадает в обработку (период, язык, точные дубли, разрешённые источники) | нет |
| Мягкий фильтр = ранжирование | после карточки | понижение позиции правилом, карточка остаётся, с объяснением | да, мгновенно, без LLM |
| Вью-фильтр | при просмотре | дропдауны дашборда (категория, важность, тип, дата, поиск) — прячут из текущего списка, балл не трогают | да |
**Почему:** без этого команда путается; каждый механизм решает свою задачу (экономия обработки /
приоритизация без потери данных / навигация).

### Р9. Защитные правила «Требует внимания» — не отключаются

**Решение:** отдельный неотключаемый набор правил: критичные изменения законодательства,
комплаенс-риски, риск штрафов/проверок/суда, репутационные кризисы, НПА на сопровождении → всегда
в блоке «Требует внимания», поверх пользовательских правил.
**Почему:** пользовательские предпочтения не должны случайно спрятать то, что несёт юридический
или репутационный риск. Пользователь может ужесточить, но не отключить.

### Р10. Семантика — слой просмотра, на сбор не влияет

**Решение:** семантическая близость и «показать по смыслу: ___» работают **только на уже собранных
карточках** — это навигация/фокус, не часть сбора или саммаризации. Эмбеддинг карточки считается
один раз после саммари; дальше только косинус. Убрал фильтр — вернулись все карточки.
**Почему:** удобство работы с готовой лентой; шум не удаляется, а убирается из поля зрения по
требованию. Ровно под целевую метрику «ценность без лишнего шума».

### Р11. Карточка стабильна к смене предпочтений

**Решение:** саммари события считается **один раз**. Правила и семантика пересчитываются свободно
без обращения к LLM. Повторная саммаризация запускается только если:
(а) изменился «медленный» профиль проекта (отрасль, отслеживаемые компании, требуемый формат
анализа), либо (б) в событие добавился новый источник.
**Почему:** предпочтения и правила меняются часто, иногда на каждый заход. Пересаммаризировать
всю ленту каждый раз — недопустимо по времени. Разделяем «что это» (LLM, редко) и «насколько это
интересно сейчас» (правила, постоянно).

## 4. Функциональные требования (сводно)

### F1. Сбор

- F1.1. Коннекторы: RSS, сайт регулятора (HTML), Telegram (веб-превью `t.me/s/`), оффлайн-архив, ручной ввод.
- F1.2. Инкрементальность по `last_fetched_at` (Р2).
- F1.3. Первичный сбор за выбранный период проекта (сутки / 7 / 15 дней / произвольный диапазон).
- F1.4. Расписание обновления: каждый час / несколько раз в день / раз в день / вручную.

### F2. Обработка

- F2.1. Очистка текста, определение языка.
- F2.2. Жёсткий отбор до LLM: период, язык, точные дубли (Р8).
- F2.3. Событийная кластеризация: объединение сообщений об одном факте (Р3).
- F2.4. Саммаризация в контексте профиля: 3–5 предложений + сущности кто/что/когда/последствия (Р4).
- F2.5. Категоризация: регуляторика / репутация / конкуренты / тренды.
- F2.6. Тип материала: НПА / новостная статья.
- F2.7. Важность: высокая / средняя / низкая.
- F2.8. Кэш саммари; повторная саммаризация только по условиям Р11.

### F3. Ранжирование

- F3.1. Балл события = сумма весов сработавших правил (Р6).
- F3.2. Правила `field` и `semantic`, действия boost / penalize / pin / hide (Р7).
- F3.3. Стартовый набор правил при создании проекта; полный CRUD правил в UI.
- F3.4. Объяснение позиции: список сработавших правил с дельтами.
- F3.5. Защитные правила «Требует внимания» — неотключаемые (Р9).
- F3.6. Пересчёт ранжирования — мгновенный, без LLM.
- F3.7. Временные правила «только для этого просмотра», не сохраняются в проект.
- F3.8. Строгий режим (`strict_mode`): понижение → скрытие ниже порога, данные не теряются.

### F4. Единый интерфейс

- F4.1. Дашборд: блок «Требует внимания» + ранжированная лента событий.
- F4.2. Фильтры: источник, дата, категория, важность, тип, статус.
- F4.3. Поиск по тексту, сущностям (полнотекстовый).
- F4.4. Семантический фокус «показать по смыслу: ___» (Р10).
- F4.5. Карточка события: саммари, сущности, тип, важность, все источники со ссылками, объяснение позиции.
- F4.6. Метрика обработки на видном месте (обработано / релевантно / скрыто как шум / время).
- F4.7. Дайджест за период с экспортом в Markdown.

### F5. Управление источниками и данными (обязательное требование кейса)

- F5.1. Добавить источник по URL (RSS / сайт регулятора / Telegram) с предпросмотром до сохранения.
- F5.2. Редактировать источник, включать/выключать, удалять.
- F5.3. Редактировать любое событие: заголовок, текст саммари, категорию, важность, тип, теги.
- F5.4. Скрыть источник или конкретное событие из ленты (данные сохраняются).
- F5.5. Ручное добавление события/документа, которого не было в источниках.
- F5.6. Отредактированные пользователем поля не перезаписываются при повторной обработке (Р11).
- F5.7. Обратная связь по событию: полезно / нерелевантно.

## 5. Нефункциональные требования

- **Производительность демо:** обработка 50–60 материалов оффлайн-датасета — минуты, не часы;
  пересчёт ранжирования всей ленты — доли секунды.
- **Автономность демо:** полный сценарий работает без внешних API (оффлайн-датасет + mock-LLM +
  локальная модель эмбеддингов).
- **Прозрачность:** любое положение карточки в ленте объяснимо списком правил.
- **Отсутствие потери данных:** скрытие и понижение не удаляют записи; всё восстановимо.
- **Простота развёртывания:** один `docker compose up` либо два процесса (api + web).

## 6. Открытые вопросы

- Конкретный LLM-провайдер и модель (OpenAI-совместимый / YandexGPT / GigaChat / локальный) —
  выбирается по наличию ключей; архитектурно не блокирует.
- Список из ≥5 конкретных источников для пресета (какие СМИ, какие регуляторы, какие TG-каналы).
- Формат и состав тестового оффлайн-датасета (структура файлов).
